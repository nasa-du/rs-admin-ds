# Contributing

This repository implements an accepted specification. Changes must not
silently diverge from it: when the spec, an ADR and the code disagree, the
latest ADR amendment wins, then the ADR body, then the specification
(spec §0). New irreversible decisions require a new ADR or an amendment.

## Workflow

1. Pick a ticket in `nasa-du/rs-admin-ds` and note the acceptance criteria it
   implements.
2. Work on a short-lived branch. Keep the change scoped to the ticket.
3. Add or update tests with the change. Acceptance criteria map to test
   names, scripts or runbook steps; do not mark an AC done without evidence.
4. Run the checks below locally.
5. Open a PR using the template. Reference the issue and the acceptance IDs
   (`AC-AUTH-…`, `AC-RBAC-…`, `AC-API-…`, `AC-FE-…`, `AC-OPS-…`, `AC-DOC-…`)
   the change affects.
6. Merge only after the required checks pass. `main` is the deployment source;
   production images come only from `main` and `v*` tags.

Commit messages follow the existing style:

```
feat(scope): imperative summary
fix(ci): what was broken and why the fix works
test(e2e): the behaviour now covered
docs(ops): the procedure that changed
```

## Required checks

Backend (PostgreSQL 18 must be reachable through `DATABASE_URL` for
integration tests):

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
DATABASE_URL=postgres://rs_admin:rs_admin_dev@127.0.0.1:5432/rs_admin \
  cargo test --workspace --all-targets
```

Frontend (use the pinned Bun 1.4.2; lockfile v2 is not readable by older
releases):

```sh
cd frontend
bun install --frozen-lockfile
bun run check        # lint, format:check, typecheck, i18n:check, test, build
bun run api:generate # only after an OpenAPI change; commit both artifacts
```

Deployment and scripts:

```sh
./scripts/generate-dev-secrets.sh
./scripts/check-deploy.sh
./scripts/check-deploy-db.sh
./scripts/check-deploy-edge.sh
./scripts/check-observability.sh
./scripts/tests/release.sh
./scripts/tests/upgrade-drill.sh
./scripts/tests/acceptance.sh
./scripts/check-acceptance-docs.sh
```

Full-stack and M6 acceptance (isolated Compose projects; destructive to their
own volumes only):

```sh
./scripts/e2e.sh
./scripts/perf.sh
./scripts/security-verify.sh
./scripts/fault-injection.sh
```

Run `security-verify.sh` before a release that changes auth, headers, CORS,
CSRF, cookies, logging or dependencies. The scheduled
[security workflow](.github/workflows/security.yml) re-runs dependency and
image scans weekly; CRITICAL findings open an issue and block the next
release until fixed or risk-accepted.

## Generated artifacts

- `backend/openapi.json` is generated by `cargo run -p rs-admin-api --bin
  openapi -- backend/openapi.json`. CI fails if the committed file changes.
- `frontend/src/api/generated/` is generated by `bun run api:generate`. CI
  fails on drift. Never edit generated files by hand.
- `Cargo.lock` and `bun.lock` are committed and must stay in sync with their
  manifests.

## Migrations

- Migrations are forward-only. SQLx records a checksum; never edit a file that
  has been released.
- Use expand/contract: add columns/tables/indexes first, keep old code working,
  remove the old shape in a later release. The `migrate` job must pass on an
  empty database and on the previous release's schema.
- Migrations run as the one-shot `migrate` container; the API never migrates at
  startup. Runtime roles get table grants from `deploy/db/grants.sql` after the
  migration.
- Update the domain catalog, OpenAPI, error codes, audit catalog, frontend
  mappings and tests together when a contract changes.

## Secrets and test data

- Never commit key material, tokens, passwords or production data. Development
  secrets live in gitignored `deploy/secrets-dev/`; production secrets live in
  `/etc/rs-admin/secrets/` (see [deploy/secrets/README.md](deploy/secrets/README.md)).
- Test users are created by test factories. The production bootstrap creates
  only the first super administrator; there are no seed users.
- Application logs, audit rows and metrics must never contain passwords,
  password hashes, temporary passwords, tokens, cookies, Authorization headers
  or key material. Usernames and emails are not application-log fields.

## Documentation

- Use the terminology in [CONTEXT.md](CONTEXT.md); do not introduce synonyms
  for the domain concepts.
- Link new operational procedures from [docs/runbooks/README.md](docs/runbooks/README.md)
  and keep alert `runbook_url` anchors valid.
- Acceptance evidence belongs in [docs/acceptance/](docs/acceptance/README.md).
  Re-run the relevant harness and update the record when behaviour changes.
- Keep the specification and ADR conflict resolutions current; an undocumented
  deviation is a defect.
